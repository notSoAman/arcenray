# Large multipart upload QA — 28 October 2026

Two explicitly authorized, disposable private uploads used the 7,316,162,017-byte Troy MP4. They used the same multipart API and 64 MiB part protocol as the clients, through disposable Clerk development accounts; this was not a browser or native-mobile UI test. No test film was published.

- The source contains HEVC video, two AC-3 audio tracks and a data track. A local probe with the identical processor binary used on Oracle rejected it with `select_one_video_and_at_most_one_audio_track`. The live worker returned only `processing_failed`; the exact underlying live exception is not exposed. This result is consistent with the local probe, but the live response does not independently identify the reason.
- Both copies were fingerprinted in 10.6 and 11.6 seconds. They uploaded concurrently in 110 parts, completing in 587.1 and 630.1 seconds. Server-side part listings confirmed the expected count and total bytes.
- The queue showed one job processing and one queued. The first returned its first `processing_failed` indication at 739.1 seconds from transfer start; the second at 925.0 seconds, including its queue wait. The harness removed each film after the first rejected attempt, avoiding repeated downloads of an already-known incompatible source. The normal worker retries failures before reporting a terminal state; this test did not measure that full retry cycle.
- Sampled Oracle readings remained healthy: the worker stayed active; the lowest observed disk free was 87 GiB and the lowest observed available memory was about 10 GiB. After the test the queue was empty, the filesystem was back to 94 GiB free, and worker scratch was 4 KiB. These are sampled observations, not precise peaks or proof of sustainable throughput.
- The test harness called the film-deletion RPC, deleted each test asset's exact private and public object keys, and checked each with a signed R2 HEAD for 404. No cleanup error was reported. A database check found no recent assets of the tested byte size, no active processing jobs, and no profile or processing job for the tracked second test account. Temporary Clerk users were removed by the harness. This does not constitute a complete bucket-wide audit.

Limitations: this establishes concurrent upload and serial queue handling of two private copies, not successful transcoding, playback, sustained saturation, or a maximum concurrent-user limit. The application currently exposes a generic processing error and can retry incompatible input repeatedly; a creator is not told that multiple audio tracks caused the rejection. The source should not be silently reduced to one language track without an explicit creator choice.
